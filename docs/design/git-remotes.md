# Design: GitHub, HTTPS and SSH git remotes

Status: built (stages 1 to 3, 2026-10-11); the acceptance checks in §5 need the user.
Extends [git review](../git-review.md). Deviations: the migration is
`019_git_remotes.sql` (018 went to teammates) and also adds `public_key` and
`host_key_offered`; re-pinning is `PUT …/forges/{id}/host-key`. The v0 spike passed: v0
rounds bridge cleanly, so `ssh` forges don't require v2.

Today a forge is a Forgejo instance reached over HTTPS with a studio-only token
`FORGE_<NAME>_TOKEN`. Sandboxes clone, fetch and push through
`https://git.studio.internal/<forge>/<owner>/<repo>.git`; pushes land in a per-sandbox
staging repo and go upstream only after a `git.push` approval. This design adds three
forge kinds and keeps everything else.

## Decisions in one table

| Question | Decision |
| --- | --- |
| Forge kinds | `forgejo`, `github` (HTTPS + token + API), `https` (any host, token, no API), `ssh` (any host, the host's SSH agent or a Studio-held key, no API) |
| Which transport for forges with an API | Always HTTPS with the token. SSH is only for kind `ssh`. |
| Guest-facing protocol | Always smart HTTP to `git.studio.internal`, whatever the upstream transport. No SSH server in the gateway. |
| SSH key | With auth `key`: ed25519, generated by Studio, one per `ssh` forge, studio-only secret `FORGE_<NAME>_SSH_KEY`. No import, no per-teammate keys. |
| Host key | Pinned at creation: Studio scans the host, the user confirms the fingerprint in the Add forge dialog. No known_hosts import, no silent TOFU. |
| SSH agent | Host-side only, never forwarded. For `ssh` forges with auth `agent` (the default), Studio's own client signs with the host's agent for fetches and approved pushes; a sandbox never reaches it. Studio does not read `~/.ssh`, `ssh_config` or proxy variables. |
| `git@host:…` in a sandbox | Rewritten to the virtual remote by managed `insteadOf` rules for hosts that have a forge; fetch and push both go through Studio. |
| Port 22 egress | No special case. Hosts without a forge are ordinary egress under the network policy. |
| Private/LAN git hosts | Refused, like every other forge and egress target. Not configurable. |
| GitHub credential | Fine-grained personal access token. Not a GitHub App, not OAuth device flow. |
| GitHub PRs | REST API with `net/http`, same `git.pr` approval as Forgejo. |
| GitLab | Push and fetch work as kind `https`. Merge-request proposals are deferred. |
| Migration | `019_git_remotes.sql` (after `018_teammates.sql`) |

## 1. Arbitrary SSH remotes

### Forge record

An `ssh` forge has a name, a base URL `ssh://<user>@<host>[:<port>]` (the form also accepts
scp syntax `git@host:` and normalizes it; the user defaults to `git`), the pinned host key and
the key secret. The host must be a public name or address, the same rule as HTTPS base URLs
(`teammates.BaseURL` with an `ssh` scheme).

### Key (auth `key`)

- Studio generates an ed25519 key when the forge is created with auth `key`, or switched to
  it (`crypto/ed25519`,
  `ssh.MarshalPrivateKey` from `golang.org/x/crypto/ssh`; `golang.org/x/crypto` is already a
  direct dependency, so no new module).
- The private key is sealed in the vault as studio-only secret `FORGE_<NAME>_SSH_KEY`: no
  host binding, never a placeholder in a sandbox, refused by the secrets API (409) like the
  forge token, shown on the Secrets page as "Forge SSH key", deleted with the forge.
- The public key (`ssh-ed25519 AAAA… sandbox-studio/<env>/<forge>`) is returned with the forge
  and shown with a copy button. The user adds it as a deploy key (one repo, write access) or
  to their account.
- Per forge, not per environment or teammate: revoking one forge's key touches nothing else,
  and a deploy key scoped to one repository is the narrowest grant most hosts offer. Who
  asked for a push is already in the approval (teammate, sandbox) and in the commits; the
  key only identifies Studio acting after the user approved.
- No key import. A new key comes from switching the forge to the agent and back, or from
  delete and re-add (the pushes it staged go with it, same as today). Studio never uses the
  user's own `~/.ssh` keys.

### Agent (auth `agent`)

- `auth` is `agent` (the default for `ssh`) or `key`. `PUT …/forges/{id}/auth` switches it:
  to `key` Studio generates a key and returns its public key; to `agent` it deletes the key.
- Studio lists the agent's keys and offers the first six, in the agent's order, the limit of
  OpenSSH's default `MaxAuthTries`; keys past it are never tried. The pinned host key still
  applies. A host that refuses every key fails with "refused the keys in your SSH agent",
  and so does one that disconnects after too many attempts.
- The agent is reached through `SSH_AUTH_SOCK` on Linux and macOS, and through the OpenSSH
  agent's named pipe `\\.\pipe\openssh-ssh-agent` on Windows (`go-winio`). Studio reads the
  environment it was started with, so an autostarted Studio needs the variable set.
- Only Studio's host-side client uses the agent, for fetches and approved pushes. The socket
  is never forwarded: no agent request on the SSH session, and no `SSH_AUTH_SOCK` in a
  sandbox. Sandboxes still go through push review.
- Slow signatures. A signature that takes `DefaultSlowSign` (2 s) or longer means the agent
  asked the user to confirm it: a hardware key touch or a password manager prompt. Studio
  records `agent_slow_at` on the forge. Settings → Git forges then shows a dismissible hint with
  "Set up a Studio key", which switches the forge to `key` and shows the public key. Dismissal is
  `agent_hint_dismissed`, per forge (`POST …/forges/{id}/dismiss-agent-hint`).
- No agent: the forge's operations fail with "SSH agent not available" and how to fix it.
  Settings → Git forges shows the same, and `studio doctor` warns (never fails) while an agent forge exists.

### Host key pinning

Pick: **scan and confirm at creation.** The Add forge dialog has two steps for `ssh`:

1. "Scan" calls `POST /forges/scan` with the base URL. Studio dials the host (public
   addresses only), runs the SSH handshake up to the host key with the preference
   ed25519, ecdsa, rsa-sha2-512, and returns key and `SHA256:` fingerprint. No
   authentication happens.
2. The dialog shows the fingerprint with "Make sure this is the fingerprint the host
   publishes"; the user ticks it and creates the forge. The confirmed
   key is stored with the forge (`host_key`, authorized_keys format).

Afterwards every connection pins exactly that key (`HostKeyAlgorithms` restricted to its
type, `ssh.FixedHostKey`). A mismatch fails the push, fetch or test with
"the host key of <host> changed (pinned SHA256:a, offered SHA256:b); check with the host's
admin, then re-pin it in Settings → Git forges". The forge row shows the same warning; re-pinning is a
new scan plus confirmation (`POST /forges/{id}/host-key`).

Not an inbox approval: the user is present in the dialog when the forge is created, and an
approval would let a sandbox's first fetch trigger the trust decision. Not known_hosts
import: it reads host files, has hashed-name and `@cert-authority` variants we'd have to
support, and is a second way to do the same thing.

### How sandbox traffic reaches Studio

The sandbox never speaks SSH to Studio. Its remote is the same virtual HTTPS remote:

```
https://git.studio.internal/<forge>/<path>.git
```

`<path>` is generalized from `<owner>/<repo>` to 1 to 8 segments (each
`^[A-Za-z0-9_][A-Za-z0-9._-]{0,99}$`, no `..`), so gitolite's `repo`, GitHub's `owner/repo`
and GitLab's `group/sub/repo` all work. The store keeps everything before the last segment
in `owner`.

**Remote mapping.** The managed git config Studio already writes at session start
(`harness.GitConfig`, `~/.config/git/config`) gets `insteadOf` rules for the environment's
forges, so existing clones and agents typing the real URL just work:

```
[url "https://git.studio.internal/gh/"]
	insteadOf = https://github.com/
	insteadOf = git@github.com:
	insteadOf = ssh://git@github.com/
[url "https://git.studio.internal/box/"]
	insteadOf = git@git.example.org:
	insteadOf = ssh://git@git.example.org/
```

Rules: the base URL's HTTPS form for `forgejo`, `github` and `https`; plus scp and `ssh://`
forms with user `git` for every kind (for an `ssh` forge, its own user and port; the scp
form only when the port is 22). When two forges share a host, the oldest one gets the
rules; the other is used with its explicit virtual URL. A `git@github.com:o/r` remote thus
travels over HTTPS with the token: the sandbox doesn't care, and one credential per forge
is enough.

**Fetch** (`info/refs?service=git-upload-pack`, `POST git-upload-pack`) for an `ssh` forge
is bridged per HTTP request: Studio opens an SSH session (pinned host key, forge key),
asks for `GIT_PROTOCOL=version=2` when the sandbox sent `Git-Protocol: version=2`, runs
`git-upload-pack '<path>'`, reads the server's advertisement up to the flush packet, then:

- `info/refs`: returns it behind the `# service=git-upload-pack` header;
- `POST`: discards it, writes the request body, closes stdin and streams stdout until EOF.

Protocol v2 is stateless by design, so this is exact. Servers that refuse the
`GIT_PROTOCOL` variable (stock OpenSSH without `AcceptEnv GIT_PROTOCOL`, e.g. plain gitolite)
answer v0; Studio then advertises v0 and bridges each stateless-RPC round as a fresh
session. Stage 3 starts with a spike against real git (`git` 2.4x over the fake server
below); if v0 rounds don't bridge cleanly, `ssh` forges require v2 and "Test" says so. The
one-time rejection message, size limits and error masking are unchanged.

**Push** is unchanged up to the approval: `info/refs?service=git-receive-pack` mirrors the
upstream refs into the staging repo (an upload-pack session over SSH instead of HTTP), the
pack is checked and staged, `git.push` is raised. On approval Studio runs
`git-receive-pack '<path>'` over SSH and sends the same update request and pack it sends over
HTTP today.

**Implementation note.** Studio does not use go-git's `transport/ssh`: it reads
`~/.ssh/config` for host and port and dials through `ALL_PROXY` from the environment, and
its dialer can't be replaced, so `gateway.DialPublic` couldn't be enforced. Instead
`internal/gitreview` gets a small `upstream` interface (advertise, upload-pack request,
receive-pack request) with two implementations: the existing go-git HTTP sessions, and an
SSH one built on `x/crypto/ssh` over a `DialPublic` connection, encoding and decoding with
go-git's public `packp` and `pktline` types. Paths are single-quoted for the remote command;
the path regex already excludes quotes. One SSH connection per request; pooling only if it
turns out to matter.

### What a sandbox can't do

- `git clone git@unknown-host:…` for a host without a forge is a plain TCP connection to
  port 22 through the gateway. The network policy decides it like any host:port (approval,
  allow or deny rule); the sandbox has no key, so it fails at authentication unless the
  agent made its own key and somebody registered it. That bypasses review and is the user's
  call; docs say so. No separate "read-only SSH through the gateway" mode: public code is
  reachable over HTTPS, and repos worth a key are worth a forge.
- No agent forwarding: the guest gets no `SSH_AUTH_SOCK` from Studio. Studio's host-side
  client may sign with the host's agent for `ssh` forges with auth `agent`; the socket is
  never forwarded into a sandbox.

### Private and LAN hosts

Refused, explicitly. Forge base URLs, scans and every upstream dial go through the public-only
rule (`DialPublic`: no private, loopback, link-local, CGNAT/Tailscale ranges), checked at dial
time so DNS can't rebind past it. A LAN forge would let a sandbox drive requests into the
user's network through Studio, choosing paths at will. Users with a homelab git server
expose it under a public name or push from the host themselves. We revisit only with a
concrete request, and then as a per-forge pinned address used solely by Studio's own
connections, never by sandbox egress.

## 2. GitHub

### Credential: fine-grained personal access token

| | Fine-grained PAT | GitHub App + device flow | OAuth App device flow |
| --- | --- | --- | --- |
| Setup | User creates a token, pastes it | Project registers and runs a public App; user installs it per account/org, then signs in | Project registers an OAuth App; user signs in |
| Scope | Chosen repos; Contents RW, Pull requests RW, Metadata R | Intersection of user and installation; good | `repo` scope: every private repo the user can reach |
| Lifetime | Up to 366 days or none (an org policy may cap it) | 8 h access token, 6-month refresh token, refresh needs no client secret for device-flow tokens | Long-lived |
| Studio work | Same as Forgejo: one studio-only secret | Device-flow UI, refresh scheduler, rotating refresh tokens in the vault, re-login after six months idle | Device-flow UI |
| Dependency on the project | None | The project operates a GitHub App indefinitely | Same, smaller |

Pick the **fine-grained PAT**. For a self-hosted single-user app it needs no infrastructure
run by the project, has the narrowest grant, fits the existing forge shape exactly and works
for git over HTTPS and the REST API alike (GitHub tokens only work for HTTPS git, which is
what the virtual remote uses anyway). Costs: one manual step, and tokens expire; Test shows
the expiry (`GitHub-Authentication-Token-Expiration` response header) and the token can be
replaced in place (below). Known GitHub limit, documented: a fine-grained token can't push
where the user is only an outside collaborator; a classic token with `repo` works there and is
accepted without special handling, but docs recommend fine-grained. The App/device flow
would change only where the credential comes from, not the adapter; we revisit if pasting
tokens turns out to be the main friction.

Token permissions (docs and the Add forge dialog spell these out): repository access "Only
select repositories"; **Contents: read and write** (fetch and push), **Pull requests: read and
write** (open PRs), **Metadata: read** (added automatically; default branch).

### Adapter

`gitreview.GitHub` implements the existing `Adapter` interface next to `Forgejo`, plain
`net/http` through Studio's public-only client, no redirects followed:

- API base: `https://api.github.com` for base URL `https://github.com`, else
  `<base>/api/v3` (GitHub Enterprise Server comes for free).
- Headers: `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`,
  `X-GitHub-Api-Version: 2022-11-28` (re-check the current version when building).
- `GitAuth`: `x-access-token:<token>` basic auth for git over HTTPS.
- `Check`: `GET /user` → login, plus the expiry header.
- `DefaultBranch`: `GET /repos/{owner}/{repo}` → `default_branch`.
- `OpenPullRequest`: `POST /repos/{owner}/{repo}/pulls` with `{title, head, base, body}` →
  `html_url`. A 422 shows `message` and the first `errors[].message` ("A pull request already
  exists for …").
- Errors are masked as today; a 301 for a renamed repo surfaces as "the repository moved to
  …; update the remote".

It plugs in where `KindGitHub` returns `ErrNotImplemented` today (`adapter`, `CheckForge`);
the integration interface in `internal/integrations` doesn't change: git review stays one
integration with `git.push` and `git.pr`, and forge kinds are adapters inside it.

### GitLab

Push and fetch work now as kind `https` (username `oauth2`, a PAT or project access token
with `write_repository`). Merge-request proposals need a `gitlab` adapter
(`POST /api/v4/projects/:id/merge_requests` with the URL-encoded path); deferred until
someone asks, roughly a day of work with the same test shape as GitHub.

## 3. Other HTTPS remotes

Kind `https`: base URL, a username (default `git`; Bitbucket wants `x-token-auth`, GitLab any)
and a token, sent as basic auth exactly like Forgejo. No API: no PR proposals, and the
default branch comes from the advertised `HEAD` symref. It unifies with the rest through one
model: **a forge is (kind, base URL, username, one studio-only credential, optional pinned
host key)**; the kind chooses the transport (HTTPS or SSH) and whether there's an API
adapter. "Test" for `https` needs a repository path (the dialog asks for one) because there
is no user endpoint; for `ssh` it authenticates and reports whether the key was accepted.

## 4. UI

Forges are on **Settings → Git forges** of each environment (they are per environment, like
secrets).

- **Add forge** dialog: a repository URL first (`git@host:owner/repo.git`,
  `ssh://user@host:port/owner/repo.git` or `https://host/owner/repo`). It fills the kind, base
  URL, short name and the path for the preview; every field stays editable.
  - Kind: Forgejo, GitHub, Other HTTPS, Other SSH. A GitHub URL over SSH becomes Other SSH
    with the agent; choose GitHub for pull requests.
  - Name in Studio, last and filled in from the host until the user types one, with the
    live preview "How sandboxes refer to this forge, in URLs like
    https://git.studio.internal/<name>/<path>.git". (It was "Short name", next to Kind, which
    confused people.)
  - GitHub: base URL prefilled `https://github.com`, token field with a link to the
    fine-grained token page and the permissions listed.
  - Other HTTPS: base URL, username, token.
  - Other SSH: `git@host` or `ssh://user@host:port`, Authentication (My SSH agent, the default,
    or A Studio key), Scan, fingerprint with a confirmation checkbox, Create. With a Studio
    key, the public key follows with Copy and "Add this key to the host with write access (a
    deploy key for one repository is enough)".
- **Forge row**: kind, base URL, remote example, Test, Delete; for token kinds "Replace token";
  for `ssh` the host-key fingerprint, the authentication with a switch to the other kind, and
  a warning with "Re-pin" after a mismatch. With the agent: "SSH agent not available" and its
  fix when Studio can't reach it, and the dismissible hint "Your SSH agent asked for
  confirmation…" with "Set up a Studio key" after a slow signature. With a key: the public key
  (copy). Test shows the GitHub token's expiry ("expires in 12 days" in amber under 14).
- **Page intro**: one sentence and a "Learn more" link to the git review guide on the docs site.
- **Secrets page**: "Forge token" / "Forge SSH key" rows, not editable.
- **Approvals** (kinds registry: one title, summary and icon per kind):
  - `git.push`: title "Push to <forge>/<path>"; summary "<teammate> in <sandbox> wants to push
    <n> commits to <branch>"; detail adds "Studio pushes over SSH to git@host:path, host key
    SHA256:…" for `ssh` forges, "over HTTPS as <login>" otherwise.
  - `git.pr` (GitHub): title "Open a pull request on GitHub"; summary "<branch> → <default> in
    <owner>/<repo>".
- **Sandbox-facing texts** (as `remote:` lines): `This environment has no forge
  "<forge>". Add it in Sandbox Studio under Settings → Git forges.`, host-key mismatch, "the forge
  refused Studio's key/token".

## 5. Schema, API, tests, docs

### Migration `019_git_remotes.sql`

- Rebuild `forges` (SQLite can't widen a CHECK): `kind IN ('forgejo', 'github', 'https', 'ssh')`,
  new `username TEXT NOT NULL DEFAULT ''`, `host_key TEXT NOT NULL DEFAULT ''`; copy rows,
  recreate the two secret-owner triggers. `secret_id` holds the token or the SSH key.
- `git_pushes` unchanged (`owner` may now contain `/`).

### Migration `021_forge_agent.sql`

- Rebuild `forges` again: `secret_id` becomes nullable (an agent forge has no secret), and
  `auth` (`agent` or `key` for `ssh`, empty for token kinds), `agent_slow_at` and
  `agent_hint_dismissed` are added. CHECKs tie them together: `auth = 'agent'` exactly when
  there is no secret. The secret-owner triggers now apply to any secret a forge holds, so a
  key or token is still a studio-only secret of the same environment. Existing `ssh` forges
  become `key`.

### API (tag `git`)

- `POST /api/environments/{env}/forges`: `kind` enum gains `https`, `ssh`; new `username`
  (https, ssh), `hostKey` (ssh, required, the scanned key the user confirmed); `token`
  required for token kinds, refused for `ssh`.
- `POST /api/environments/{env}/forges/scan` `{baseUrl}` → `{hostKey, fingerprint, algorithm}`.
- `POST /api/environments/{env}/forges/{id}/host-key` `{hostKey}`: re-pin.
- `PUT /api/environments/{env}/forges/{id}/token` `{token}`: replace in place, keeping staged
  pushes (needed because PATs expire).
- `POST …/forges/{id}/test` gains optional `repo` (required for `https`).
- `Forge` gains `username`, `publicKey`, `hostKeyFingerprint`, `hostKeyMismatch`, and with
  agent auth `auth`, `agentSlowAt` and `agentHintDismissed`. `secretId` is absent for agent
  forges.
- `POST …/forges` for `ssh` takes `auth` (`agent`, the default, or `key`); `token` stays
  refused for `ssh`.
- `POST …/forges/parse-url` `{url}` → kind, base URL, short name not yet taken in the
  environment, path. A URL that isn't a repository is 422.
- `PUT …/forges/{id}/auth` `{auth}`: switches an `ssh` forge; returns the forge with its public
  key for `key`.
- `POST …/forges/{id}/dismiss-agent-hint`: hides the slow-sign hint for the forge (204).
- `GET /api/system/ssh-agent`: whether the agent is reachable, its keys (type, fingerprint,
  comment), and the message and fix when it isn't.

### Tests (fakes only)

- `TestGitHubAPI`: `httptest` fake for `/user` (expiry header), `/repos/o/r`, `/repos/o/r/pulls`
  (201 and 422); checks Bearer and version headers and that the token never appears in errors.
- `TestGitHubForgeEndToEnd`: the existing TLS fake forge serving git and the API, through the
  virtual remote: clone, push, approve, PR approval.
- `TestCheckForge`: new kinds, scp and `ssh://` parsing, ports, refused private/loopback hosts
  and credentials in URLs.
- `TestRepoPaths`: one to eight segments, `..`, depth and character limits.
- `TestInsteadOfRules` (harness): rules per kind, oldest forge wins a shared host.
- Fake SSH server (`x/crypto/ssh`, in process; the service gets a `Dial` override for tests,
  since `DialPublic` refuses loopback): scan returns the fingerprint; pinned-key mismatch and
  unknown client key are refused; the exec command is quoted; no agent forwarding or env other
  than `GIT_PROTOCOL` is requested. With a real `git` on the host (skipped otherwise, like
  `TestRealGit`) the fake runs `git upload-pack`/`receive-pack` on a temp bare repo: clone and
  fetch through the virtual remote with v2 and with v0, push staged, approval pushes over SSH.
- API: SSH forge creation requires `hostKey` and returns `publicKey`; the key and token never
  appear in any response; the secrets API answers 409 for both; token replacement keeps pushes.
- Agent (fakes only, never a real agent: `SSH_AUTH_SOCK` is set to a test socket or cleared):
  an `x/crypto/ssh/agent` keyring on a temp unix socket drives fetch, push and approval; a
  slow keyring records the slow sign; a refused key set, an empty agent and a missing one fail
  with their messages; at most six keys are offered. Pasted URLs parse to kind, short name and
  path. The store migrates existing forges and enforces the agent and secret CHECKs and the
  studio-only trigger. `studio doctor` warns, not fails, for agent forges without an agent.

### Docs

`docs/git-review.md` (kinds, remote mapping, SSH, host keys, GitHub token permissions),
the git review status in the v2 plan (now in `docs/git-review.md`), the secrets page help
text.

### Acceptance checks that need the user

1. GitHub: create a fine-grained PAT for one test repo (Contents RW, Pull requests RW), add a
   `github` forge, Test shows the login and expiry. In a sandbox,
   `git clone git@github.com:<you>/<repo>.git` works (rewritten), a branch push shows up for
   review, approving pushes it, the PR approval opens a PR on GitHub.
2. SSH: add an `ssh` forge for a real host (Codeberg over SSH, or a VPS/gitolite), compare the
   scanned fingerprint with the host's published one, add the public key as a deploy key, then
   clone, push, approve as above.
3. Host key change: re-pin flow against the same host with a deliberately wrong stored key.

## 6. Staged plan

1. **GitHub** (smallest, most useful): adapter, `CheckForge`, token replacement endpoint,
   UI kind, tests. No migration needed (`github` is already in the CHECK).
2. **Remote paths and mapping**: 1–8 segment paths, `insteadOf` rules in the managed git
   config, kind `https` with username, migration 018, Test with `repo`.
3. **SSH**: spike v0/v2 bridging against real git; `upstream` interface; SSH upstream with
   pinned keys; key generation; scan and re-pin endpoints; UI; fake-server tests.
4. **Docs and acceptance** with the user's GitHub account and an SSH host.
5. Later, on demand: GitLab MR adapter; GitHub App device flow if token pasting hurts.
