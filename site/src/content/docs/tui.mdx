`studio tui` is a keyboard client of the Studio that is already running on this machine. It
shows the sandboxes of an environment, creates, forks and suspends them, and saves and restores
their checkpoints. It answers approvals and reviews git pushes, chats with a sandbox's teammate, follows the network Activity, and opens a sandbox's
terminal in full screen. Everything else stays in the browser, and the TUI prints the address
of the page where you need it.

## Start it

Start Studio as usual, then, in another terminal on the same machine:

```sh
studio tui
```

If Studio isn't running, the TUI says so and shows the command that starts it. It needs an
interactive terminal, and it signs in as you without asking for anything: only your user can
read the data that makes this possible, so run it on the machine Studio runs on. Over SSH, run
it there.

## Keys

The keys are the same on every screen, and they can't be changed. The key bar at the bottom
shows the ones that apply where you are, and `?` lists them all.

| Key | On the sandbox list |
|---|---|
| `↑` `↓` or `j` `k` | move the cursor, over sandboxes and their sessions |
| `1` to `9` | go into that session: an agent, a chat or a terminal |
| `enter` | go into the session under the cursor; on a sandbox, open it: its facts, its open ports, and the same keys |
| `tab` | the next session that waits for you |
| `n` | create a new sandbox |
| `t` | open the sandbox's main terminal (it must be running) |
| `T` | start the teammate's agent in a new terminal and open it |
| `s` | start, stop or resume the sandbox |
| `z` | suspend the sandbox; `s` resumes it |
| `f` | fork the sandbox |
| `h` | the sandbox's checkpoints |
| `d` | delete the sandbox; the TUI asks first |
| `c` | the newest chat with the sandbox's teammate, or a new one |
| `C` | a new chat |
| `a` | approvals, from every environment |
| `l` | Activity: connections and decisions |
| `e` | switch environment |
| `/` | filter by name, teammate or template |
| `?` | help |
| `q` | quit |

`esc` or `q` goes back from every other screen. The header counts the approvals waiting in
every environment, and the terminal rings its bell once when a new one arrives.

## Sessions

Under each sandbox, the list shows what you can go into: its agents running in a terminal,
the newest three chats with its teammate (`+ n older` shows the rest), and its other terminals.
The first nine are numbered. Press a number and you're in: a terminal opens, and a chat opens
ready for your prompt. `Ctrl-]` leaves a terminal, and `esc` a chat, back to the list with the
cursor where you were. To switch to another agent, press `Ctrl-]` and its number.

```
Sandbox Studio · Default                               2 blocked · ● 2 approvals
────────────────────────────────────────────────────────────────────────────────
  ● Running   blub             Iris      node-22+python-… up 2h 14m
    1  ✓      claude                     agent · done
▸   2  ○      Fix the login form         chat · 3m ago
    3         main                       terminal · attached
  ● Running   api-refactor     Finn      go@2             up 12m     2 approvals
    4  ▲      codex                      agent · blocked
    5  ▲      Port the parser to go      chat · blocked
    6         main                       terminal
```

Each agent shows what it's doing:

- `●` working: a chat's turn runs, or the agent's terminal is printing;
- `▲` blocked: it waits for you. For a chat, that's a permission; for an agent in a terminal,
  an approval in its sandbox;
- `✓` done: it finished since you last looked. It stays marked until you go in;
- `○` idle, and `·` when the sandbox doesn't say (it started before this version of Studio).

`tab` jumps to the next blocked agent, then to the next done one. The header counts the
working and the blocked ones.

## New sandbox

`n` asks whose sandbox it is (a teammate, or none), what it starts from (the base image or one
of the environment's templates), and its name, which is also its hostname: lowercase letters,
digits and dashes. `enter` goes on and `esc` goes back a step. Studio then creates the sandbox,
and the TUI shows the steps as they happen, the image pull with its progress, as the browser
does. Once the sandbox is ready it opens. If the create fails, you see the step and the reason,
and `d` deletes the sandbox so you can try again. `esc` leaves the create to finish on its own.

## Fork, suspend and checkpoints

`f` forks the sandbox: a new sandbox with a copy of its disks. The TUI asks for the name at the
bottom, and suggests one that ends in `-fork`. `enter` forks, `esc` cancels. The fork's
progress then shows as a new sandbox's does.

`z` suspends a running sandbox. `s` resumes it.

`h` lists the sandbox's checkpoints, newest first. Each shows its name, whether the schedule
took it (auto) or you did (manual), and its age. A checkpoint holds the disks, not the running
programs.

- `n` saves a checkpoint. Type a name, or press `enter` alone to name it after the time. The
  sandbox must be running or stopped.
- `r` restores the checkpoint under the cursor. The TUI asks first, and `y` restores. Stop the
  sandbox first. What changed since the checkpoint is lost.

Deleting and renaming checkpoints, and their schedule, are in the browser.

## Ports

A running sandbox's page lists its open ports, with each one's preview address. In a terminal
that shows links, you can open the address from there. The list refreshes every three seconds.

A preview needs a login the first time. Open it once from the Ports section of the sandbox's
page in the browser. After that, the address from the TUI opens in that browser for eight
hours.

## Approvals

Requests from one sandbox that come in close together are one card, as they are on the web.
A card lets you:

- **Allow or deny** a network request. `y` and `n` make a rule for the host pattern and the
  scope you chose; `o` and `O` answer only this connection, with no rule; `1` allows it for
  an hour; `i` ignores it. When the browser opens a new site, `w` allows the site for the
  rest of that browser session, with no rule.
- **Choose what the rule covers:** `p` changes the host pattern (for a browser request, also
  its method and path), `s` the scope (the environment, your teammate's sandboxes, or this
  sandbox), and `x` any port instead of the default ports. For a browser request, `s` picks
  who the rule covers: its browser, all browsers, or the browsers and the sandboxes.
- **Decide a group:** `A` allows every host, `D` denies every host, and `r` reviews them one by
  one.
- **Review a git push:** `enter` opens the push in a pager: the repository, branch and change,
  the commits, and the diff with added lines in green and removed ones in red. Scroll with the
  arrows, `pgup`/`pgdn` (or `b`/`space`), `g` and `G`. Then `y` approves and pushes it, `n`
  rejects it, and `i` ignores it. A pull request shows its title and description, and `y`
  opens it.

The other cards are decided with their own keys:

- **Browser action:** `y` allows the click or the typing, `n` denies it, `i` ignores it. `r`
  makes the answer hold for every such action on that site.
- **Browser credential:** `y` fills the secret, `n` denies it, `i` ignores it. The agent sees
  only the secret's name.
- **Memory share:** `y` shares the fact with every teammate, `n` declines, `i` ignores it.
- **Memory conflict:** `1` keeps fact A and `2` keeps fact B; the other one is retracted. `i`
  leaves it for later. To keep both or edit one, `enter` prints the address of the memory page.
- **Agent permission:** the agent's options are numbered. Press the number of the one you
  want, or `i` to ignore the request.

## Chat

A chat's number or `enter` opens it; `c` opens the sandbox's newest chat, and `C` or `n` (in a
chat) starts a new one. A sandbox needs a teammate to chat with.

```
Sandbox Studio · Default                                            ● 1 approval
────────────────────────────────────────────────────────────────────────────────
Fix the login form · blub                                                  Ready
› The login form doesn't submit on enter. Can you fix it?

  ▸ Thought it through
  ▸ Read src/login.tsx                                                      done
  ▸ Edit src/login.tsx                                                      done

Fixed

The form used a `div` as its button, so enter did nothing. It is a real submit
button now:

    <button type="submit">Sign in</button>

- Enter submits the form.
- The button is focusable.



────────────────────────────────────────────────────────────────────────────────
p prompt  ↑/↓ tools  pgup scroll  n new chat  esc/q back  ? help
```

The transcript streams as the agent works. Thoughts and tool calls are folded to one line:
`↑` and `↓` move between them, and `enter` expands one to show its files, its diff or its
output. `p` writes a prompt at the bottom: `enter` sends it, `ctrl+j` starts a new line, and
`esc` puts it aside. `x` stops the turn that runs. Headings are bold and code is indented;
there is no other formatting.

When the agent asks for a permission or asks a question, you answer it in the chat. The
choices are listed under it.

- A permission: press the number of an option, or `i` to ignore it.
- A question: press the number of a choice, or `r` to type an answer and `enter` to send it.
  `i` skips the question. A question with several fields is answered in the browser; its keys
  print the chat's address.

## Activity

`l` shows the network log of the environment, newest first: each connection a sandbox made,
with its verdict, and each decision on a request, with how it was made. On a sandbox, `l`
shows only that sandbox; elsewhere `/` filters by sandbox name. `enter` opens an entry with the
rule that decided it: its host pattern, action, ports, which sandboxes it covers, where it came
from, its hits and when it expires. Without a rule, it says what decided instead, such as the
curated list or a once decision. The log refreshes every two seconds. Rules are edited in the
browser; `r` prints the address.

## Look, wide terminals and the mouse

On a terminal with colors, the TUI uses the web's colors. Each area has its own hue: network,
git, browser, memory and chat. Status dots are colored, and approvals show as cards. From 81
columns, the header becomes tabs.

Wider terminals use the extra room:

- From 120 columns, Home shows the selected sandbox beside the list, with its CPU and memory,
  the first approval waiting, its terminals and ports, and its history. When the sandbox's
  teammate's browser runs, the pane ends with the page it is on and a small picture of it, on
  terminals with 256 colors or more.
- The git review lists the changed files, and `[` and `]` jump between them.
- From 160 columns, Home adds the selected sandbox's network as it happens: each connection,
  how long ago, its host and its verdict.
- From 160 columns, the diff is side by side, and `v` toggles it.
- The words a changed line changes are highlighted.
- What an action did, or an error, shows for 3 seconds at the top right.

The mouse works too:

- A click selects a row, and a double click opens it.
- The wheel scrolls.
- A click on a tab opens it, and a click on a key, on a card or in the key bar, presses it.
- Hold shift to select text as usual.

`STUDIO_TUI=plain studio tui` gives the plain look shown above, with no mouse. So do
`NO_COLOR` and terminals without colors. Every screen still fits 80×24.

## Terminal

`t` opens the sandbox's main terminal, the one the browser opens first, and a terminal's number
opens that one. From a shell, `studio shell <sandbox> [terminal]` does the same. The sandbox's
screen takes over your terminal, and your keys go to it, as in any other terminal. Resizing
your window resizes the sandbox's. Press `Ctrl-]` to go back to the TUI. If the sandbox ends the
terminal, you see that, and the next key returns you to the TUI.

## Stays in the browser

Settings, providers, teammates, templates, the rules editor, the network page, memory, the
browser, secrets and the git settings are in the browser. So are a few answers: keeping both
facts of a memory conflict, questions with several fields, and a preview's first login. The
TUI prints their addresses where it has a key for them, and `?` shows where the browser is.
